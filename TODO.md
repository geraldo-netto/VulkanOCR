| VOCR-0001 | critical | m | **Text rotated 30°–60° is silently dropped: `_oriented` never enforces "`rw` is the short side".** `detection.py:153-167` normalises orientation with angle thresholds copied from nihui's `ppocrv5.cpp` (`if not vertical and angle < 30: angle += 90; rw, rh = rh, rw`). With the installed OpenCV 5.0.0, `minAreaRect` returns angles in `[-90, 0)`, so a line skewed 30°–60° comes back as e.g. `(302.6, 19.8, -45.0)`; line 159 maps it to `135.0`, which is not `< 30`, so the swap never fires and `rw` stays the *long* side. `crop_region` (`recognition.py:20`) then computes `target_width = max(int(region.height * 48 / max(region.width, 1e-6)), 1)` = `int(19.8*48/302.6)` = **3 px**, and the rec net sees a 48x3 sliver. Measured end-to-end twice with `models_for()` on `cv2.putText("Vulkan 1234")`: `0deg -> ['Vulkan 1234']`, `10deg -> ['Vulkan 1234']`, `25deg -> ['lkan 1234']`, **`35deg -> ['2']`, `45deg -> ['1']`, `55deg -> ['34']`, `70deg -> ['4']`**. The failure is not an empty answer — it is a confident wrong one, which is worse: a caller cannot tell a rotated line from a line that says `1`. The crop widths behind those reads are 13, 19 and 26 px against the ~265 px a 25° line gets. Note the loss begins *before* the swap: 25° already drops `Vu` from the front. The corpus only carries `skew-5deg`/`skew-12deg` and `samples/` only `sample-rot7.png`/`sample-rot25.png`, so nothing covers the broken band. Fix: after the branches, unconditionally enforce `if rw > rh: rw, rh = rh, rw; angle += 90` (or derive orientation from `long/short` rather than from the raw angle), and add a rotation sweep test at 35°/45°/55°. |
