| VOCR-0047 | high | s | **Exit hangs on a dead worker's unsent crops.** A patch assigned to a worker that died sits in the request `Queue`'s buffer; the feeder thread blocks in `Connection._send` forever (no reader, pipe full) and multiprocessing's atexit `_finalize_join` joins that feeder — the process never exits (observed: faulthandler stack, death-repro). `close()` must `close()` and `cancel_join_thread()` every request channel (and the replies queue) after the workers are down, so unsent data is dropped instead of awaited. Blocks the live suite: tests pass, the run then hangs and times out. |
| VOCR-0036 | high | s | Stale worker replies poison the read after a failure: when `read` raises mid-page — `_answer`'s worker-died refusal (src/vulkanocr/parallel.py:103-127) or a Ctrl-C — workers still holding crops finish and put "done" replies into `self._replies`, and nothing drains them; the next `read` (parallel.py:171-181) consumes them first, so a `crop_index` from the previous page lands in the new page's `results` — wrong region/text pairing, or IndexError when the new page has fewer crops. The dead worker also stays in `_cost`/`_requests`, so it keeps being assigned work (parallel.py:166). Tag messages with a read generation and drain mismatches, or mark the pool broken at the first refusal. |
| VOCR-0038 | medium | s | `ParallelOcr.__init__` leaks on a failed start: if any worker dies before its "ready" (bad driver, OOM), `_answer` raises out of the startup loop (src/vulkanocr/parallel.py:97-101) with no try/finally — `self._primary` (~700 MiB VRAM, the leak `OcrEngine.close` exists for) and every already-started worker process are never closed. Wrap the startup in try/except that calls `close()`. |
| VOCR-0039 | medium | s | The dispatcher's prices are frozen at the startup probe: the comment at src/vulkanocr/parallel.py:40-44 calls the probe "the seed price the dispatcher plans with before it has seen real crops from this device", but `self._cost` is written once (parallel.py:101) and never updated — "done" replies carry no timing (parallel.py:64, 171-176). A device whose 96-column white probe is unrepresentative (fp16, clocks ramping, asymmetric det load) mis-prices every assignment for the pool's whole life. Time real crops and refine the price, or make the docstring stop promising it. |
| VOCR-0042 | medium | s | Every pooled engine loads a net it never runs: `OcrEngine.__init__` always loads det+rec (src/vulkanocr/engine.py:168-170), but `ParallelOcr` workers only ever `recognise` (parallel.py:58-64) — N devices hold N unused detection nets' Vulkan allocations — and device 0 carries two full engines at once, the parent's `_primary` (parallel.py:80) plus its own worker (parallel.py:88-95). Load nets lazily or let a caller ask for the half it needs. |
| VOCR-0043 | medium | s | The dispatcher has no test a machine without two GPUs can run: the pricing/assignment logic (`assign`, src/vulkanocr/parallel.py:147-169), the slow-device commitment guard, `_assembled`'s ordering, and `_answer`'s dead-worker refusal are exercised only by the live-GPU suite (tests/test_live_gpu.py:110-130). All are pure logic over injectable queues/engines; the stale-reply behaviour of VOCR-0036 has no test at any lane. |
| VOCR-0044 | low | xs | The CLI never closes the engine it opens: `main` builds `engine = _reader(arguments)` (src/vulkanocr/cli.py:80) with no `with`/`close()` — worker processes are left to daemon-kill and the VRAM to process exit, the exact pattern `OcrEngine.close`'s docstring (engine.py:183-190) was written against. One context manager fixes it. |
| VOCR-0045 | low | xs | The CLI hides `undecoded_regions`: `OcrResult` carries it precisely so a caller can tell "clean page" from "the detector saw something the recogniser could not read" (src/vulkanocr/engine.py:114-127), but cli.py prints only the lines and their count (cli.py:111-115), so both cases print identically — the invisibility the field's own docstring warns about. One line when the count is non-zero. |
